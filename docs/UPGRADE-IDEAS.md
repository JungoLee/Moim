# UPGRADE-IDEAS — DB·기능 고도화 아이디어 (목록 관리 전용)

> **바로 적용하지 않는다.** 사용자가 항목을 골라 지시할 때만 구현한다.
> D1(SQL) 전환으로 새로 가능해진 것 위주 — 각 항목에 "필요한 DB 변화 + 기대 효과"를 함께 적는다.
> 확정되어 진행할 항목은 PLAN.md 로 옮기고 여기서 지운다.

## A. 기존 데이터를 그대로 활용 (스키마 변경 없음·소규모)

1. **공통 빈 시간 자동 취합** (PLAN Phase 2 잔여의 구체안)
   - 모임 멤버들의 `events` 를 SQL 로 겹침 집계 — Mongo 시절엔 앱 코드로 풀어야 했던 걸 쿼리 하나로: 멤버 전원의 일정을 날짜별 GROUP BY → 아무 일정도 없는 날 = 후보일. 비공개 일정도 "존재 여부"만 쓰므로 가시성 침해 없음
   - DB 변화: 없음. 효과: 모임 방의 수동 날짜 찍기 전에 "이미 다들 비어 있는 날"을 먼저 제안

2. **연차 계산기 → 캘린더 원클릭 등록**
   - 추천된 연차일을 버튼 한 번으로 `events` 에 일괄 INSERT (`db.batch`). `origin_kind='leavePlan'` 스냅샷을 남기면 시간요청 일정처럼 출처 표시 가능
   - DB 변화: 없음(origin_kind 값만 추가). 효과: 계산기(유입용 공개 도구) → 가입·활성 사용자 전환 고리

3. **관리자 통계 고도화**
   - 이미 있는 `created_at` 들로 가입 추이·주간 활성(일정 작성 기준)·모임 활동을 날짜 GROUP BY 집계. 프론트는 admin 페이지에 미니 차트
   - DB 변화: 없음. 효과: 성장 지표를 서비스 안에서 바로 확인

17. **코드 입력칸(`CodeBoxes`) 을 모임·그룹 코드에도 재사용**
    - 인증코드 6자 전환(2026-08-21)으로 만든 컴포넌트를 모임 입장 코드·그룹 가입 코드(둘 다 8자) 입력에도 쓴다. 붙여넣기 한 번에 채움·화면 복귀 시 클립보드 자동 채움·칸 이동을 그대로 얻는다
    - 필요한 변경: `CodeBoxes` 의 고정 `CODE_LEN = 6` 을 `length` prop 으로, 허용 문자·대문자화 여부도 prop 으로(모임/그룹 코드는 대문자 정규화). DB 변화 없음
    - 효과: 초대 코드를 손으로 옮겨 적는 흐름이 가장 이탈이 큰 지점 — 로그인에서 검증된 UX 를 그대로 이식

## B. 테이블 1개 추가 수준

4. **안읽음 서버 영속** (PLAN "다음 작업"의 구체안)
   - `room_reads(room_id, user_id, last_read_at, PK(room_id,user_id))` 1테이블. 방 목록 쿼리에 `created_at > last_read_at` 카운트 서브쿼리
   - 효과: 기기 바꿔도 안읽음 유지. 현재 클라 lastRead 방식의 상위 호환

5. **알림 피드 통합**
   - `notifications(id, user_id, kind, ref_id, read, created_at)` — 친구요청·시간요청·모임 변경을 한 테이블로. 지금 흩어져 있는 배지 폴링(친구요청·시간요청 각각)이 `GET /api/notifications` 하나로 합쳐진다
   - 효과: Nav 빨간 점 폴링 일원화 + "모임 이름이 바뀌었어요" 같은 신규 알림 확장 기반

6. **모임 날짜 확정 흐름**
   - `rooms` 에 `confirmed_date TEXT` 컬럼(또는 `room_decisions` 테이블). 방장이 집계 결과에서 확정 → 전원 캘린더에 비공개 일정 자동 생성(시간요청 accept 의 양쪽 생성 패턴 재사용, `origin_kind='room'`)
   - 효과: "모두 되는 날 찾기"의 마지막 단계가 완성됨 — 지금은 찾고 나서 각자 알아서 등록해야 한다

7. **초대 토큰** (PLAN Phase 7 의 구체안)
   - `invite_tokens(token, kind, ref_id, scope, expires_at)` — 방/캘린더 초대를 코드 대신 만료 있는 토큰 URL 로. 워커가 토큰 검증 후 제한된 뷰 제공
   - 효과: 비회원에게 "이 모임 달력 보기만" 공유 가능

18. **매직 링크 로그인 — 코드 입력 없이 메일에서 클릭 한 번**
    - 카드형 인증 메일(2026-08-18)에 코드와 **함께** "바로 로그인" 버튼을 넣는다. 링크에는 코드 대신 1회용 서명 토큰을 실어 워커가 검증 → JWT 발급
    - DB 변화: `login_codes` 재사용 가능(같은 행의 소비 여부로 1회성 보장). 분리하려면 `link_hash` 컬럼 하나
    - 효과: 메일 앱↔브라우저 왕복이라는 가장 큰 이탈 구간 제거. 모바일에서 특히 크다
    - ⚠️ 메일 보안 스캐너·프리페치가 링크를 먼저 열어 코드를 소모시킬 수 있다 → 즉시 로그인시키지 말고 "로그인 계속" 확인 화면(POST)을 한 번 경유해야 한다. 6칸 코드 입력은 폴백으로 남긴다

19. **`mail_rate` 를 범용 레이트 리밋 테이블로 승격**
    - 지금 메일 발송에만 쓰는 `mail_rate(key, count)` 를 `rate_limit(key, count)` 로 일반화하고 `overRate(scope, id, limit)` 헬퍼를 친구요청·모임 생성·방 댓글 등 남용 가능한 경로에 붙인다. 키에 스코프를 접두어로 넣으면 테이블 구조는 그대로
    - DB 변화: 테이블 이름만(컬럼·지난 날짜 키 정리 로직 재사용)
    - 효과: 스팸 방어가 발송 경로 하나에만 있는 현재의 공백을 메운다. 악용 징후가 보일 때 하면 되는 성격

## C. Workers 플랫폼 기능 활용

8. **실시간 채팅 — Durable Objects + WebSocket** (PLAN Phase 4)
   - 방마다 DO 인스턴스 1개가 WebSocket 팬아웃, 메시지는 D1 `room_comments` 에 영속(현행 테이블 그대로). 6초 폴링 제거
   - 효과: 진짜 실시간 + 폴링 요청량 대폭 감소. ⚠️ DO 는 유료 플랜 필요 여부 확인 후 진행

9. **주간 요약 알림 — Cron Triggers**
   - `wrangler.toml` 에 `[triggers] crons` + 워커 `scheduled()` 핸들러. "이번 주 일정 N개, 대기 중 시간요청 M건" 을 Resend 로 발송
   - DB 변화: 없음(수신 동의 컬럼 `users.weekly_digest` 정도). 효과: 재방문 트리거. 전제였던 발송 수단·레이트 리밋은 충족(2026-08-18 Resend 활성) — 단 무료 쿼터 하루 100통 안에서 수신 동의자에게만

10. **requireAuth 의 D1 read 캐시 — KV**
    - 모든 인증 요청이 사용자 존재 확인으로 D1 을 1회 읽는다(PLAN 한계 항목). KV 에 `user:<id> → 1` 을 TTL 5분으로 캐시하면 대부분의 요청에서 D1 read 제거. 탈퇴 시 KV 삭제로 유령 세션 차단 유지
    - 효과: 지연·D1 사용량 감소. 트래픽이 늘기 전엔 불필요 — 보류 기준: D1 일일 read 가 무료 한도의 10% 넘을 때

11. **iCal 구독 내보내기**
    - `GET /api/calendar.ics?token=<서명토큰>` — 내 일정을 iCal 텍스트로 렌더(워커에서 문자열 생성, 라이브러리 불필요). 구글/애플 캘린더가 주기 폴링
    - DB 변화: 없음(구독 토큰은 JWT 서명 재사용 가능). 효과: "내 캘린더 앱에서도 보인다" — 이탈 방지. ⚠️ 토큰 유출 시 일정 노출이므로 폐기(재발급) 수단 필수

16. **이벤트 이메일 알림 — 시간요청·친구요청 수신 시**
    - Resend 발송 활성화(2026-08-18)로 이제 가능해진 것. 요청 생성 핸들러(`requests.js`·`friends.js`)에서 수신자에게 "OO님이 시간을 요청했어요" 메일 — 접속 안 한 사용자를 다시 부르는 유일한 채널
    - DB 변화: 수신 동의 컬럼(`users.notify_email` INTEGER) 정도. 효과: 요청→수락 전환율 상승. ⚠️ 무료 쿼터(일 100통)·스팸 인상 주의 — 종류별 동의와 일일 상한 필요

## D. 코드 구조 (기능 변화 없음 — 여유 있을 때)

14. **`holidays.ts → leave.ts → datetime.ts` 우회 의존 정리**
    - `leave.ts:6-7` 이 `addDays` 재수출 + `toKey = dateKey` 별칭을 두고 있어(기존 import 호환용 shim), `holidays.ts` 가 날짜 유틸을 `datetime` 이 아니라 `leave` 에서 가져온다. `holidays.ts` 를 `datetime` 직접 참조로 바꾸고 shim 을 걷어내면 의존 방향이 단순해진다
    - 주의: `toKey` 를 쓰는 호출처가 여러 곳이라 이름 정리까지 하면 diff 가 커진다. 기능 변화 0이지만 리뷰 부담이 있어 별건으로 분리

15. **`Nav` 공통 레이아웃화** — PLAN "다음 작업" 에도 있음. route group 레이아웃으로 올리면 페이지 이동 시 리마운트(깜빡임)가 사라진다. 정적 export 와도 무관하게 적용 가능

20. **메일 템플릿 공용 껍데기 분리**
    - `worker/mailer.js` 의 카드형 HTML(2026-08-18)이 로그인 코드 전용으로 하드코딩돼 있다. `buildMail({ title, lead, body, footer })` 로 껍데기만 떼어내면 주간 요약(9번)·이벤트 알림(16번)이 같은 디자인을 재작성 없이 쓴다
    - 기능 변화 0. 전제: 두 번째 메일 종류가 실제로 생길 때 하는 게 맞다(지금 하면 사용처 1개짜리 추상화)

## E. 검색·콘텐츠

12. **일정·댓글 검색 — SQLite FTS5**
    - D1 은 FTS5 가상 테이블을 지원. `events(title, memo)`·`room_comments(text)` 인덱스로 "그 약속 언제였지?" 검색
    - DB 변화: FTS 가상 테이블 + 동기화 트리거. 효과: 데이터가 쌓일수록 가치 상승. 초기엔 LIKE 검색으로도 충분할 수 있음 — 규모 보고 판단

13. **공휴일 데이터의 DB 화**
    - 현재 `lib/holidays.ts` 하드코딩(2026–2031)을 `holidays(date, name)` 테이블로 옮기면 임시공휴일을 배포 없이 반영. 연차 계산기·모임 집계(공휴일 표시)가 같은 출처를 쓴다
    - 트레이드오프: 정적 export 프론트가 API 를 한 번 더 불러야 함 — 오프라인 계산기 특성이 약해진다. 임시공휴일 빈도를 보고 판단
