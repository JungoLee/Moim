## A. 기존 데이터를 그대로 활용 (스키마 변경 없음·소규모)

1. **공통 빈 시간 자동 취합** (PLAN Phase 2 잔여의 구체안)
   - 모임 멤버들의 `events` 를 SQL 로 겹침 집계: 멤버 전원의 일정을 날짜별 GROUP BY → 아무 일정도 없는 날 = 후보일. 비공개 일정도 "존재 여부"만 쓰므로 가시성 침해 없음(2.0 의 `GET /api/calendar/friends` 가 이미 같은 원칙 — 시간만 싣는다)
   - DB 변화: 없음. 효과: 모임 방에서 손으로 찍기 전에 "이미 다들 비어 있는 날"을 먼저 제안 — 히트 달력/사람×날짜 표에 '캘린더상 빔' 표시를 겹치는 식

2. **연차 계산기 → 캘린더 원클릭 등록**
   - 추천된 연차일을 버튼 한 번으로 `events` 에 일괄 INSERT (`db.batch`). `origin_kind='leavePlan'` 스냅샷을 남기면 시간 요청·모임 확정 일정처럼 출처 표시 가능 — 색·배지는 `eventColor()`·일정 팝업 출처 안내 한 곳에 갈래만 더한다(옛 23번)
   - DB 변화: 없음(origin_kind 값만 추가). 효과: 계산기(유입용 공개 도구) → 가입·활성 사용자 전환 고리

3. **관리자 통계 고도화**
   - 지금 `/api/admin/stats` 는 표별 전체 건수만 센다. 이미 있는 `created_at` 들로 가입 추이·주간 활성(일정 작성 기준)·모임 활동(확정 수)을 날짜 GROUP BY 집계, admin 화면에 미니 차트
   - DB 변화: 없음. 효과: 성장 지표를 서비스 안에서 바로 확인. ⚠ 집계도 D1 읽기 한도(계정 공용)에 들어가니 관리자 화면 열 때만

28. **그룹으로 모임 만들기** (그룹 × 모임 엮기)
    - 새 모임 팝업에서 내 그룹을 고르면 그 멤버를 `room_members` 에 바로 넣는다(한 batch). 지금은 방을 만든 뒤 코드/링크를 따로 돌려야 한다
    - DB 변화: 없음. 효과: "늘 모이는 사람들"의 모임 시작이 한 번에. 결정 필요 — 동의 없이 넣을지, 초대 알림(5번)을 보내고 수락 시 넣을지

29. **홈 '누가 언제 비나' 표에서 바로 시간 요청**
    - 표 테마 홈의 빈 칸(친구 × 날짜 × 오전/오후/저녁 띠)을 누르면 시간 요청 팝업을 그 친구·날짜·시간대로 채워 연다. 받는 사람 미리 고르기(`/requests?to=`)는 이미 있다 — 날짜·시각 인자만 더하면 된다
    - DB 변화: 없음. 효과: "빈 시간 보기 → 약속 제안"이 한 화면에서 끝난다

## B. 테이블 1개 추가 수준

4. **안읽음 서버 영속** (PLAN "다음 작업"의 구체안)
   - `room_reads(room_id, user_id, last_read_at, PK(room_id,user_id))` 1테이블. 방 목록 쿼리에 `created_at > last_read_at` 카운트 서브쿼리
   - 효과: 기기 바꿔도 안읽음 유지. 지금은 이 브라우저 `localStorage`(`moim_chat_seen_<id>`) 기준

5. **알림 피드 통합**
   - `notifications(id, user_id, kind, ref_id, read, created_at)` — 친구 요청·시간 요청·모임 변경(확정·이름 변경)을 한 테이블로. 지금 틀(`useShell().inbox`)이 따로 부르는 받은 요청 2개 API 가 `GET /api/notifications` 하나로 합쳐진다
   - 효과: 홈 배지 일원화 + "모임 날짜가 정해졌어요" 같은 신규 알림 확장 기반

7. **초대 토큰** (PLAN Phase 7 의 구체안)
   - `invite_tokens(token, kind, ref_id, scope, expires_at)` — 방/캘린더 초대를 코드 대신 만료 있는 토큰 URL 로. 워커가 토큰 검증 후 제한된 뷰 제공
   - 효과: 비회원에게 "이 모임 달력 보기만" 공유 가능

18. **매직 링크 로그인 — 코드 입력 없이 메일에서 클릭 한 번**
    - 카드형 인증 메일에 코드와 **함께** "바로 로그인" 버튼을 넣는다. 링크에는 코드 대신 1회용 서명 토큰을 실어 워커가 검증 → JWT 발급
    - DB 변화: `login_codes` 재사용 가능(같은 행의 소비 여부로 1회성 보장). 분리하려면 `link_hash` 컬럼 하나
    - 효과: 메일 앱↔브라우저 왕복이라는 가장 큰 이탈 구간 제거. 모바일에서 특히 크다
    - ⚠️ 메일 보안 스캐너·프리페치가 링크를 먼저 열어 코드를 소모시킬 수 있다 → 즉시 로그인시키지 말고 "로그인 계속" 확인 화면(POST)을 한 번 경유해야 한다. 6칸 코드 입력은 폴백으로 남긴다

19. **`mail_rate` 를 범용 레이트 리밋 테이블로 승격**
    - 지금 메일 발송에만 쓰는 `mail_rate(key, count)` 를 `rate_limit(key, count)` 로 일반화하고 `overRate(scope, id, limit)` 헬퍼를 친구 요청·모임 생성·방 대화 등 남용 가능한 경로에 붙인다. 키에 스코프를 접두어로 넣으면 테이블 구조는 그대로
    - DB 변화: 테이블 이름만(컬럼·지난 날짜 키 정리 로직 재사용)
    - 효과: 스팸 방어가 발송 경로 하나에만 있는 공백을 메운다. opnae 공용 Resend 하루 100통이 한 서비스 남용으로 바닥나는 것도 막는다

30. **웹 푸시 알림** — 휴대폰·PC 알림
    - 형제 프로젝트(Gilo·task, 2026-10-12)에 들어간 패턴 재사용: `push_subscriptions(user_id, endpoint, p256dh, auth, created_at)` + VAPID 키(시크릿) + 서비스 워커. 시간 요청·친구 요청 받음, 모임 날짜 확정, (선택) 모임 대화
    - DB 변화: 표 1개. 효과: 접속 안 한 사람을 다시 부르는 채널 — 메일(16번)과 달리 쿼터 부담 없음. ⚠ 정적 export 라 서비스 워커 파일은 `public/` 에, iOS 는 홈 화면에 추가한 경우만

31. **반복 일정**
    - `events` 에 `repeat_rule`(예: 매주 화·목) + `repeat_until` 칸. 목록·친구 바쁜 시간 조회에서 기간 안 회차를 펼쳐 돌려준다(저장은 한 행)
    - DB 변화: 칸 2개(마이그레이션). 효과: 알려진 한계 "반복 미지원" 해소, Phase 5 근무표·'매주 모임'의 바탕. 회차 하나만 바꾸기·지우기 예외 처리는 범위를 정해야 한다

## C. Workers 플랫폼 기능 활용

8. **실시간 채팅 — Durable Objects + WebSocket** (PLAN Phase 4)
   - 방마다 DO 인스턴스 1개가 WebSocket 팬아웃, 메시지는 D1 `room_comments` 에 영속(현행 테이블 그대로). 6초 폴링 제거
   - 효과: 진짜 실시간 + 폴링 요청량 대폭 감소. ⚠️ DO 는 유료 플랜 필요 여부 확인 후 진행

9. **주간 요약·모임 리마인더 — Cron Triggers**
   - `wrangler.toml` 에 `[triggers] crons` + 워커 `scheduled()` 핸들러. "이번 주 일정 N개, 대기 중 시간 요청 M건", "내일 '○○ 모임' 확정일이에요"(확정된 방의 `confirmed_start` 하루 전)를 Resend 메일 또는 웹 푸시(30번)로
   - DB 변화: 없음(수신 동의 컬럼 `users.weekly_digest` 정도). 효과: 재방문 트리거. 메일이면 무료 쿼터 하루 100통(opnae 공용) 안에서 수신 동의자에게만. ⚠ 형제 프로젝트에서 cron 이 등록됐는데 실행되지 않은 일이 있었다 — 첫 실행을 꼭 확인

10. **requireAuth 의 D1 read 캐시 — KV**
    - 모든 인증 요청이 사용자 존재 확인으로 D1 을 1회 읽는다(PLAN 한계 항목). KV 에 `user:<id> → 1` 을 TTL 5분으로 캐시하면 대부분의 요청에서 D1 read 제거. 탈퇴 시 KV 삭제로 유령 세션 차단 유지
    - 효과: 지연·D1 사용량 감소. 보류 기준: D1 일일 read 가 무료 한도의 10% 넘을 때 — 단 한도는 opnae 계정 공용이라 다른 앱 사정도 같이 본다

11. **iCal 구독 내보내기**
    - `GET /api/calendar.ics?token=<서명토큰>` — 내 일정을 iCal 텍스트로 렌더(워커에서 문자열 생성, 라이브러리 불필요). 구글/애플 캘린더가 주기 폴링
    - DB 변화: 없음(구독 토큰은 JWT 서명 재사용 가능). 효과: "내 캘린더 앱에서도 보인다" — 이탈 방지. ⚠️ 토큰 유출 시 일정 노출이므로 폐기(재발급) 수단 필수

16. **이벤트 이메일 알림 — 시간 요청·친구 요청 수신 시**
    - 요청 생성 핸들러(`requests.js`·`friends.js`)에서 수신자에게 "OO님이 시간을 요청했어요" 메일 — 접속 안 한 사용자를 다시 부르는 채널
    - DB 변화: 수신 동의 컬럼(`users.notify_email` INTEGER) 정도. 효과: 요청→수락 전환율 상승. ⚠️ 무료 쿼터(일 100통, opnae 공용)·스팸 인상 주의 — 종류별 동의와 일일 상한 필요. 웹 푸시(30번)가 먼저면 메일은 폴백으로

27. **모임 대화 증분 폴링 — D1 읽기 줄이기**
    - 지금 대화 6초 폴링(`refreshComments`)과 30초 새로고침이 둘 다 `GET /api/rooms/:id` 로 방 전체(멤버·찍은 날 전부·대화 전부)를 다시 읽는다. `GET /api/rooms/:id/comments?after=<createdAt>` 로 새 대화만 받고, 찍은 날은 30초 새로고침에만 맡긴다
    - DB 변화: 없음(`idx_room_comments_room (room_id, created_at)` 이미 있음). 효과: 방을 띄워 둔 사용자 1명당 읽기 행 수가 크게 준다 — D1 무료 읽기 한도는 opnae 계정 전체 공용이고 2026-10-12 92% 까지 찬 적이 있다. 8번(DO)으로 가기 전 값싼 단계

## D. 코드 구조 (기능 변화 없음 — 여유 있을 때)

14. **`holidays.ts → leave.ts → datetime.ts` 우회 의존 정리**
    - `leave.ts` 가 `addDays` 재수출 + `toKey = dateKey` 별칭을 두고 있어(기존 import 호환용 shim), `holidays.ts` 가 날짜 유틸을 `datetime` 이 아니라 `leave` 에서 가져온다. `holidays.ts` 를 `datetime` 직접 참조로 바꾸고 shim 을 걷어내면 의존 방향이 단순해진다(`holidays.ts` 의 `parse` 도 `datetime` `parseDateKey` 와 겹친다)
    - 주의: `toKey` 를 쓰는 호출처가 여러 곳(연차 계산기 화면 포함)이라 이름 정리까지 하면 diff 가 커진다. 기능 변화 0이지만 리뷰 부담이 있어 별건으로 분리

20. **메일 템플릿 공용 껍데기 분리**
    - `worker/mailer.js` 의 카드형 HTML 이 로그인 코드 전용으로 하드코딩돼 있다. `buildMail({ title, lead, body, footer })` 로 껍데기만 떼어내면 주간 요약(9번)·이벤트 알림(16번)이 같은 디자인을 재작성 없이 쓴다
    - 기능 변화 0. 전제: 두 번째 메일 종류가 실제로 생길 때 하는 게 맞다(지금 하면 사용처 1개짜리 추상화)

37. **'그룹에 넣기' 3벌 공용화**
    - 친구 목록(`friends/page.tsx`)·친구 캘린더(`u/page.tsx`)·프로필 팝업(`UserProfileModal`)이 같은 `POST /api/tiers/:id/members` + 토스트 + 그룹 다시 받기를 각자 갖고 있다. 다시 받기 실패 처리가 조금씩 달라(조용히 넘김 / 오류 토스트) 2026-10-13 리팩토링에서 보류했다
    - 합칠 때 실패 처리를 하나로 정해야 한다(동작이 아주 조금 바뀐다)

38. **`ColorWheel` 인라인 스타일 → 모듈**
    - 밝기 슬라이더에 `style={{ width: 168, marginTop: 12 }}` 가 남아 있다(인라인은 데이터 값만 — design-system 1장). 외부 부품(`@uiw/react-color`)에 넘기는 값이라 className 이 같은 요소에 먹는지 확인하고 옮긴다

39. **바깥 바탕 클릭·가이드 카드의 `div onClick` 정리**
    - 접근성 규칙(design-system 9장 'div 에 onClick 금지')의 남은 예외: `Modal`·`AccountDrawer`·`ConfirmHost` 의 바탕(scrim) 클릭 닫기, `GuideHost` 설명 카드 클릭 '다음'. 키보드로는 ESC·버튼으로 같은 일을 하므로 급하지 않다. 바탕은 `<button aria-label="닫기">` 로 깔거나 예외로 명시

## E. 검색·콘텐츠

12. **일정·대화 검색 — SQLite FTS5**
    - D1 은 FTS5 가상 테이블을 지원. `events(title, memo)`·`room_comments(text)` 인덱스로 "그 약속 언제였지?" 검색
    - DB 변화: FTS 가상 테이블 + 동기화 트리거. 효과: 데이터가 쌓일수록 가치 상승. 초기엔 LIKE 검색으로도 충분할 수 있음 — 규모 보고 판단

13. **공휴일 데이터의 DB 화**
